# Advanced civil authored exchange

`client/src/lib/advancedCivilExchange.ts` supplies a bounded version 1 source exchange for the advanced alignment in `civilAlignment.ts`. It is separate from the older `civil.ts` polyline LandXML exporter. The new contract retains exact authored alignment JSON and copied terrain inputs; calculation results are freshly derived from those captured inputs. Every exchange declares `certification: false`.

## Source and API contract

`captureAdvancedCivilExchange({ alignmentSource, reference, terrain?, notices? })` validates and copies authored inputs. `parseAdvancedCivilExchange(unknown)` accepts a version 1 object or bounded JSON text; `serializeAdvancedCivilExchange(unknown)` produces the source JSON that the parser accepts. `analyzeAdvancedCivilExchange(unknown)` returns `{ source, alignment, report, notices }` using the current analyser. `buildAdvancedCivilLandXml(unknown)` recomputes from the same source and exports the supported native geometry. An analysis bundle is a review/report artifact, not an importable authored source: its `source` member is the versioned import contract.

The source fields are exactly `version`, `kind: "groundwork-advanced-civil"`, `certification: false`, `units`, `alignmentSource`, `reference`, `terrain`, and `notices`. Unknown fields, sparse arrays, extra own array fields, non-finite values, unsafe references, duplicate horizontal terrain points, duplicate faces, degenerate faces and incompatible unit/reference declarations are rejected. Alignment fields and segment records must have the exact supported shape. The original alignment JSON string is retained verbatim after validation; normal JSON parsing semantics apply to that string. The existing alignment parser remains responsible for its numerical and continuity limits.

The fixed unit record is `{ linear: "m", elevation: "m", area: "m2", volume: "m3", heading: "degree", grade: "percent", curvature: "1/m" }`. It describes authored inputs: `headingDeg` is degrees, grades and superelevation are percentages, and curvatures are reciprocal metres. Derived `headingRad` values and the station CSV retain their explicitly named radian unit. Coordinates, heights, station lengths and terrain must already be normalized to metres before capture. This exporter applies no conversion.

`reference` contains exactly `{ crs, axisOrder: "east-north", verticalDatum, source, sourceUnits, projectFrame }`. The current coordinate declaration is `LOCAL`, EPSG:3857, or WGS84 UTM EPSG:32601–32660/32701–32760. EPSG:4326 is accepted only as original source-unit metadata, not as the civil coordinate frame. The vertical datum is a bounded authored statement retained unchanged, including an explicit statement that it is unknown if appropriate. `source` identifies the declaration or preparation source. These declarations are not proof of georeferencing, metre normalization, datum accuracy or engineering adoption.

`sourceUnits` is null or the exact record `{ horizontalCrs, horizontalUnit, axisOrder, elevationUnit, horizontalFactorToMetres, elevationFactorToMetres }`. Supported length-unit factors are metre 1, international foot 0.3048, and US survey foot 1200/3937. Geographic source coordinates require `degree`, `lon-lat` and a null horizontal length factor. Supported EPSG projected coordinates require metre/east-north source declarations. LOCAL source coordinates cannot be relabelled as projected coordinates or vice versa. A non-null record preserves the original declared units and preparation factors independently of the normalized exchange units; it does not reapply them. A null record produces an explicit notice that no original normalization record was supplied.

`projectFrame` is null or `{ projectId, projectCrs, originEastingM, originNorthingM, originApplied }`. It records whether an origin was already applied before capture. Export does not add that origin, rotate axes, project geographic coordinates, or transform height datums. No coordinate-system base-point `Start` is written, so an already applied origin is not added again. Source survey files and richer original metadata remain separate immutable project artifacts.

Captured notices and terrain warnings are retained as authored history. Fresh analyser/review notices are returned separately as a deduplicated union and written to LandXML metadata. An empty captured notice list provides no evidence of currently valid or complete geometry. Calculation/report values supplied on import are rejected rather than trusted; recalculation after an implementation change may produce different sampled results while the historical inputs/notices remain preserved.

## Native LandXML subset

The export uses the LandXML 1.2 namespace, explicit metric units, an authored coordinate-system declaration and two-dimensional `northing easting` horizontal coordinates. Heights belong to the separate vertical profile. Straight segments become `Line`; signed-radius arcs become `Curve` with an absolute radius, computed centre and `ccw`/`cw` rotation. Full-circle and multiple-turn arcs are unsupported. Optional direction-angle attributes are omitted: the exported coordinates, lengths, centres, radii, rotation and spiral tangent intersection define geometry without guessing between differing consumer direction conventions.

Varying-curvature clothoids become `Spiral` with length, start/end radius, rotation, `spiType="clothoid"`, parameter constant and start/PI/end coordinates. An exactly zero endpoint curvature is `INF` radius; finite endpoint radii must not exceed 1,000,000,000,000 m. This subset requires no curvature sign crossing, a total turn below 180 degrees, a stable finite intersection of the endpoint tangents, and the supported forward/backward tangent arrangement. Constant-curvature, inflecting, singular or multiple-turn spirals fail with an explicit error. They are never silently replaced by sampled `Line` elements. Their full definitions remain available in the authored JSON exchange. Spiral endpoints retain the existing bounded Simpson integration approximation; native semantic records do not establish numerical accuracy or consumer interoperability.

The vertical profile starts and ends with `PVI`. Each authored parabolic record supplies `ParaCurve` length and its tangent-intersection PVI, not an elevation sampled on the parabola. For BVC station `s`, length `L` and incoming grade `g`, the PVI station is `s + L/2` and PVI elevation is `elevation(BVC) + g*L/2`, with grade expressed as a ratio. Native profile export requires exact authored incoming-grade continuity; the existing analyser's small grade-continuity allowance remains available in JSON analysis.

When every sampled section is complete and has at least two points, sections are exported as `CrossSects/CrossSect` with ground `CrossSectSurf/PntList2D` and design `DesignCrossSectSurf/CrossSectPnt` offset/elevation pairs. The current civil analyser uses positive offsets to the left of the increasing-station direction. LandXML section offsets are positive right, so offsets are negated and sorted for export. Elevations are absolute in the declared unchanged height frame. If any section has incomplete daylight/terrain coverage or fewer than two points, version 1 omits the entire `CrossSects` family, with incomplete/total omitted counts and the exact incomplete stations in metadata. This prevents consumers interpolating a continuous section set across skipped gaps. Full sampled records remain in the recomputed JSON analysis. The analyser excludes adjoining incomplete volume intervals, and the reported quantified length remains visible. Coverage between complete sampled stations/offsets is still unverified.

The `GroundworkAdvancedCivil` Feature metadata records the version/scope, false certification flag, authored reference, exact alignment-source string, approximate cut/fill volumes, quantified length and every returned notice. It is descriptive provenance, not a national highway standard, earthwork certification, geotechnical assessment or consumer-specific conformance claim. The captured terrain itself remains in the JSON source; this module does not export a second terrain surface or proprietary corridor assembly, pavement layers, bulking, drainage design, station equations or independently designed superelevation.

The XML vertical coordinate-system name qualifies the original reference as an authored unchanged label with heights normalized to metres. The exact original datum/vertical-CRS declaration remains in Feature/source metadata. In particular, a source label such as EPSG:6360 or EPSG:5702 is not advertised as the effective metre vertical CRS after feet-to-metre scaling. No alternate authority code or datum transformation is inferred.

## Bounds and integration

Alignment source text is at most 100,000 characters; the source JSON output is at most 2,000,000 characters and LandXML at most 5,000,000. Terrain capture permits 3–2000 points and 1–4000 valid faces. Captured notices and terrain warnings each permit 100 dense entries of at most 4000 characters; the returned deduplicated notice union is bounded at 300 entries. Derived section output is bounded at 20,000 points. Exceeding a bound fails explicitly; records are not silently truncated.

The existing analyser retains its 100 horizontal/vertical/superelevation records, 1000 km length, 500 stations, 50,000 terrain queries and 10,000 Simpson substeps per spiral-position bounds. Source capture alone does not execute those calculations, so a supported source JSON remains available when calculation budgets or native LandXML geometry limits prevent an analysis/export.

Workbench integration must capture the current normalized terrain and its reference together with the exact alignment draft when calculating. Derive `sourceUnits` from the captured `PreparedSurvey.provenance` declaration/factors, carry preparation warnings into notices, and record the resulting CRS/unchanged datum and origin-applied state. For independently authored metre geometry, declare the metre frame and set unavailable original source-unit records to null. Do not fill captured CRS/reference from later edits to transient CRS controls. Changing alignment, terrain, constraints or reference inputs clears the captured calculation/export artifact. JSON source, CSV/report and LandXML actions should use that same captured source; display returned notices visibly. Catch native export errors so the source JSON remains available. Saved workspaces may persist the source declaration, but restored reports must be recalculated from it.

ExchangeWorkbench implements this capture as workspace version 4. Saved calculations retain the authored civil source separately from the current survey controls; restoration validates the exact alignment draft/source identity and recomputes from the captured terrain/reference rather than importing result claims. Versions 1–3 retain drafts, with legacy civil calculated flags cleared pending capture under this contract; version 3 terrain declarations remain usable. Source JSON import calculates its own captured terrain, displays that reference and leaves the current survey controls separate. Recalculation explicitly uses the current survey/reference. Import of a valid source whose analysis exceeds a budget fails without replacing current state; its original JSON file remains the source authority. A separate current-source export validates/serializes without calculation, so computation/native geometry limits do not prevent retention of supported authored inputs. File generation checks prevent a later completed read from replacing a restored workspace.

The JSON file reader bounds UTF-8 input at 6,000,000 bytes, rejects malformed UTF-8, and then applies the parser's 2,000,000-character limit; this accommodates valid Unicode source exports. Surface summaries retain terrain/normalization notices first and explicitly identify overflow; full raw source warnings remain in the saved survey. Direct segment enum fields require actual supported strings without coercion.

## Primary references and verification status

- [buildingSMART Finland LandXML header guidance](https://buildingsmart.fi/infra/bSI_LandXML12_MVD/pages/1_Header.html): units and coordinate/height declarations.
- [buildingSMART Finland route/alignment guidance](https://buildingsmart.fi/infra/bSI_LandXML12_MVD/pages/3_Alignments.html): native horizontal and vertical element meanings, clothoid endpoint radii and tangent PI, and parabolic PVI/length.
- [buildingSMART Finland road/section guidance](https://buildingsmart.fi/infra/bSI_LandXML12_MVD/pages/4_RoadsStreets.html): offset/elevation section representation and right-positive offsets.
- [Autodesk Civil 3D supported LandXML data](https://help.autodesk.com/cloudhelp/2026/ENG/Civil3D-UserGuide/files/GUID-4D10ABA5-5EA0-41A8-BB61-C3F446CE7C6B.htm): consumer handling of northing/easting coordinates, actual alignment stationing and native alignment/profile/section families.

This is a source-inspected implementation subset, not full conformance to the referenced model view or LandXML schema. The primary landxml.org 1.2 XSD was inaccessible during this review. No app, repository code, tests, compiler, type check, lint, numerical sample, build, preview, native tool or external validator was executed. Numerical accuracy, pathological geometry, browser performance and independent XML/import interoperability remain unverified.
