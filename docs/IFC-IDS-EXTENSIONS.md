# IFC mapped geometry and typed IDS metadata subset

This Phase 4 source increment extends `client/src/lib/ifcGeometry.ts` and `client/src/lib/bimValidation.ts`. The existing import, source-preserving name patch, mesh export and validation APIs remain available. This is bounded browser exchange coverage; IFC schema validation, IDS certification and native authoring acceptance remain external.

## Geometry contract

`importIfcGeometry(source)` accepts one declared schema from `IFC_SUPPORTED_SCHEMAS`: IFC2X3, IFC4, IFC4_ADD1, IFC4_ADD2, IFC4_ADD2_TC1, IFC4X3, IFC4X3_ADD1 or IFC4X3_ADD2. These identifiers enable only the implemented shared representation subset. Unknown, ambiguous and future/draft names are rejected rather than inferred from an IFC4 prefix. Exactly one project and length unit are required. Geometry is emitted in metres with IFC Z-up coordinates.

Nested mapped items may reuse the existing supported tessellation, polygonal BRep/surface and extrusion representations. The target must be `IfcCartesianTransformationOperator3D`, with positive uniform scale in `1e-9..1e9`, three-dimensional origin and either all axes omitted or all three supplied. Explicit normalized axes must be orthogonal and right handed within `1e-10`; partial-axis derivation, nonuniform scaling, reflection and shear are rejected. Those are product limits, not claims that IFC prohibits those transformations.

**MappingOrigin must resolve exactly to an identity 3D placement.** Nonidentity origins receive unsupported geometry issues and their source records remain intact. Source review found that [IfcOpenShell v0.8.0 placement utility](https://github.com/IfcOpenShell/IfcOpenShell/blob/v0.8.0/src/ifcopenshell-python/ifcopenshell/util/placement.py) and [its mapped-item geometry implementation](https://github.com/IfcOpenShell/IfcOpenShell/blob/v0.8.0/src/ifcgeom/mapping/IfcMappedItem.cpp) compose target and origin directly. The inspected schema prose does not independently establish the inverse-origin convention originally proposed for this implementation. Identity-only support avoids exporting wrongly transformed coordinates while that convention and benchmark acceptance remain unresolved.

For supported identity origins, the matrix is the current occurrence transform followed by the target. The outer representation context is applied once. Nested mapped source contexts are validated but their world-coordinate placements are not applied a second time. Every graph path checks cycles/depth; shared maps can be reused by separate occurrences. Existing global limits remain 20 MB STEP source, 100,000 entities, 1,000,000 parsed values, 200,000 geometry traversal steps, 250,000 emitted vertices and 500,000 triangles. Transformed coordinates must be finite within the existing 100,000 km bound. Unsupported geometry is reported per product; original STEP remains the export authority.

## Metadata and IDS contract

Imported products retain the legacy string `properties` and `propertyTypes`. New optional `propertyValues` records hold typed/raw scalar and lexical values, property/set/type STEP IDs, occurrence/type origin, support issues, and explicit/project unit provenance. Supported nominal scalars require an explicit IFC type; unwrapped values and unknown types remain unsupported. The parser retains enumeration-token provenance, so a quoted '.T.' cannot become an IfcBoolean and an enumeration cannot become an IfcLabel. Besides the six primitive types below, retained measure coverage is limited to length/positive length/nonnegative length, area, volume, mass, time, plane angle and positive plane angle. Unit references, SI prefix and simple conversion-factor/base references are retained; general measure conversion is not performed. `attributePresence` distinguishes an unset attribute from a present empty string. Current exported name patches must set Name presence when creating an empty or non-empty name.

One supported direct `IfcRelDefinesByType` supplies type property sets. The type class must match the occurrence class plus TYPE; the documented WallStandardCase-to-WallType relation is also allowed. Cross-class and generic IFC2X3 mappings remain incomplete. Occurrence single-value properties override matching actual property-set/name pairs while preserving other inherited members. Different pairs such as set `A.B`/name `C` and set `A`/name `B.C` share a legacy dotted key but cannot override one another; that collision remains ambiguous across either origin. Multiple type assignments, duplicate flattened property keys, unresolved relationships and unsupported sets/property forms remain incomplete. Duplicate ambiguity also reaches product metadata, so an occurrence override cannot erase it. Assignment/traversal work is bounded globally at 200,000 steps, with at most 32 retained issues per ambiguous property record. No inheritance-chain search, quantity extraction or IFC2X3 generic flow occurrence/type class remapping is performed. An authored empty name patches an unset source Name to a present empty STEP string; equal names skip editing only when the original source already contains that string.

`validateIds(document,xml)` supports literal exact entity classes, selected occurrence/type `predefinedType`, four string attributes and single-value properties. Selected predefined layouts are wall, slab, roof, column, beam, member, plate, covering, door and window; other class layouts remain unsupported. Assigned type predefined information takes precedence; USERDEFINED resolves only to the authored type ElementType or occurrence ObjectType, rather than also matching the USERDEFINED enum token. A missing/empty custom value is incomplete. Door/window occurrence indexes use their actual PredefinedType field, after height and width.

Entity literals must be an exact class from `IFC_METADATA_PRODUCT_CLASSES`: IFCWALL, IFCWALLSTANDARDCASE, IFCSLAB, IFCROOF, IFCCOLUMN, IFCBEAM, IFCMEMBER, IFCPLATE, IFCCOVERING, IFCDOOR, IFCWINDOW, IFCSTAIR, IFCSTAIRFLIGHT, IFCRAMP, IFCRAMPFLIGHT, IFCBUILDINGELEMENTPROXY, IFCBUILDINGELEMENTPART, IFCFURNISHINGELEMENT, IFCFURNITURE, IFCSPACE, IFCSITE, IFCBUILDING, IFCBUILDINGSTOREY, IFCOPENINGELEMENT, IFCFOOTING, IFCPILE, IFCFLOWSEGMENT, IFCFLOWFITTING, IFCFLOWTERMINAL, IFCFLOWCONTROLLER, IFCFLOWMOVINGDEVICE, IFCFLOWSTORAGEDEVICE, IFCENERGYCONVERSIONDEVICE, IFCDUCTSEGMENT, IFCPIPESEGMENT, IFCCABLESEGMENT, IFCDUCTFITTING, IFCPIPEFITTING, IFCVALVE, IFCPUMP, IFCSANITARYTERMINAL, IFCAIRTERMINAL and IFCLIGHTFIXTURE. The list describes parser coverage across supported schemas, rather than schema-specific instantiability. A different class cannot become a passing empty optional selection. Standard enum values compare in their uppercase STEP spelling; authored custom type values retain case and compare exactly, so mixed-case USERDEFINED labels are supported.

Applicability limits must explicitly use one of the three documented states: `1/unbounded` (required), `0/unbounded` (optional), or `0/0` (prohibited). Missing, coerced, finite-count and other states are unsupported. Prohibited applicability ignores requirements during model checking, including an absent requirements group. Required/optional specifications still need a supported requirements group. This is a literal interpretation subset rather than XML-schema validation of the entire IDS document.

Property value constraints require explicit `dataType`. Supported types are IFCLABEL, IFCTEXT, IFCIDENTIFIER, IFCBOOLEAN, IFCINTEGER and IFCREAL. Boolean XML literals use true/false/0/1; integers require safe integer values; real literals require finite decimal/scientific values. Primitive values compare exactly without guessed unit conversions or tolerances. Whole-property prohibition detects an existing property even when its nominal value is unset. Optional properties require a constraint. Attribute prohibition distinguishes whole-attribute absence from a prohibited literal value, including present empty strings. Required/applicability attribute matching rejects empty strings, as shown by the official [empty-string attribute failure case](https://github.com/buildingSMART/IDS/blob/development/Documentation/ImplementersDocumentation/TestCases/attribute/fail-attributes_with_empty_strings_always_fail.ids). Source presence still matters: an authored empty Name fails a constrained optional attribute, whereas an unset Name is allowed, following the official [optional empty-string failure case](https://github.com/buildingSMART/IDS/blob/development/Documentation/ImplementersDocumentation/TestCases/attribute/fail-an_optional_attribute_fails_if_empty.ids). Whole-attribute prohibition also rejects an authored empty Name.

Measure data-type/value normalization, restrictions, enumerations/lists/tables, quantities, classification, material and part-of facets remain unsupported. Ambiguous or unsupported metadata cannot narrow applicability into a false pass. Exact IFC4X3_ADD2 IDS interpretation is required for that family; earlier IFC4X3 identifiers can be imported but receive incomplete IDS schema coverage. Findings/checks are bounded at 20,000/200,000 and literal/specification/output text is bounded. Reports continue to declare `certification: false`; unsupported coverage yields `incomplete`.

## Deferred acceptance

Only source inspection and primary-document review were performed. No app, repository calculation, test, build, typecheck, preview or native IFC engine was run. Independent acceptance should cover identity/nested mapping transforms, nonidentity-origin rejection, context application, unit scales, cyclic/budget graphs, exact-pair type/occurrence override, dotted-key and duplicate ambiguity, token-kind and malformed scalar rejection, boolean/integer/real literals, empty/unset property and attribute cardinalities, the three applicability states, USERDEFINED custom-value resolution, unsupported schema/facet rejection and source-preserving rename round trips. Full IFC/IDS conformance, nonidentity mappings, representation completeness, structural model conversion and certified exchange remain unfinished operational/coverage work.
